# Cocos MCP 功能分析与超越 Pro 的产品规格

核对日期：2026-10-29。目标环境：Cocos Creator 3.8.8 + Codex 桌面客户端。分析基线为 0.2.0；当前工程已更新至 0.8.0 开发预览，增量见 [覆盖记录](COVERAGE.md)、[预制体工作流](PREFAB-WORKFLOWS.md)、[资源、动画与构建](RESOURCE-ANIMATION-BUILD.md)、[字体与 UI](TYPOGRAPHY-UI.md)、[场景视图与参考图](SCENE-VIEW-REFERENCE.md) 和 [UI 自适应布局](UI-LAYOUT.md)。下文标为 0.2.0 的对照保留历史，不能作为当前实现清单。

结论：把对方 Pro 的全部公开能力作为最低需求基线，再以实际游戏开发任务的完成率、可恢复性、交互体验和上下文成本证明优势。当前尚未对齐 Pro，不能用“有通用脚本接口”“工具更少”代替工作流验收。

### 2.1 源码中需要区别对待的支持

1. **预览/构建不是自动交付。** `runProject` 与 `buildProject` 实际打开 builder 面板，返回说明让用户手动继续；不能把 success 当成预览已运行或构建产物已生成。[project-tools.ts:109](https://github.com/DaxianLee/cocos-mcp-server/blob/a5db895b3299dccd78979ca0268193e4b6ebf037/source/tools/project-tools.ts#L109)
2. **实时控制台捕获有缺口。** `setupConsoleCapture` 是空实现，`addConsoleMessage` 未找到调用方；不能将内存 console 通道视为可靠的真实编辑器日志。独立的磁盘日志读取功能仍然存在。[debug-tools.ts:15](https://github.com/DaxianLee/cocos-mcp-server/blob/a5db895b3299dccd78979ca0268193e4b6ebf037/source/tools/debug-tools.ts#L15)
3. **工具开关主要过滤清单。** 调用分派未检查当前启用清单；空启用清单又回退到全部工具。隐藏工具不是执行权限隔离。[mcp-server.ts:102](https://github.com/DaxianLee/cocos-mcp-server/blob/a5db895b3299dccd78979ca0268193e4b6ebf037/source/mcp-server.ts#L102)、[调用入口:138](https://github.com/DaxianLee/cocos-mcp-server/blob/a5db895b3299dccd78979ca0268193e4b6ebf037/source/mcp-server.ts#L138)
4. **资源优化未对外启用。** asset_optimize 的工具定义已被注释；asset_analyze 明确只开放 dependencies/manifest。不能把残留 helper 或注释中的 unused/validate_refs 算成已支持功能。[asset-advanced-tools.ts:62](https://github.com/DaxianLee/cocos-mcp-server/blob/a5db895b3299dccd78979ca0268193e4b6ebf037/source/tools/asset-advanced-tools.ts#L62)
5. **HTTP 需要区分协议实现与网络访问控制。** 公开版是手写 HTTP/JSON-RPC，绑定 127.0.0.1；代码设 CORS `*`，未见 Bearer 校验或 Origin 限制。不能说它默认暴露公网，也不能说它具有我们的随机令牌机制。[mcp-server.ts:75](https://github.com/DaxianLee/cocos-mcp-server/blob/a5db895b3299dccd78979ca0268193e4b6ebf037/source/mcp-server.ts#L75)、[HTTP 入口:164](https://github.com/DaxianLee/cocos-mcp-server/blob/a5db895b3299dccd78979ca0268193e4b6ebf037/source/mcp-server.ts#L164)
6. **管理界面确实存在。** Vue 面板、开关、端口/自动启动设置、工具配置与持久化均有代码；工具管理器默认 5 个配置槽，存在配置导入/导出方法。README 将“工具自定义”列为 Pro 优势，不能因此否认公开版已有工具启用配置。
7. **没有发现专用截图和鼠标键盘工具，也没有自动化测试脚本。** 这是所审公开提交的范围；不能推断 Pro 同样缺失。

公开版有相当宽的接口覆盖，但“99% 编辑器控制”没有公开可复现的完整覆盖标准。它适合作为需求目录，不能作为 100% 自动开发承诺的证据。

### 3.1 Pro 值得吸收的八项设计

- **统一节点寻址：** UUID、层级路径、名称；名称歧义的处理方式未公开。
- **UI 上下文识别：** UI 父节点下自动添加 UITransform，降低 AI 忘配组件的概率。
- **返回设计分辨率与可见范围：** 创建/修改后提示越界；减少盲调参数。
- **JSON 场景构建：** 一次描述层级，自动处理 Canvas/Camera/组件。
- **参考设计图叠加：** 场景中查看目标设计稿，辅助搭建。
- **节点树缓存：** README 声明 2 秒 TTL、写入后失效。
- **失败回滚：** README 明确宣称 builder/composite 通过 snapshot 自动回滚；其场景、资源、外部副作用和崩溃恢复边界未实测。
- **动态截图：** 官网声明截取场景视口并配合 AI 回看和回归；没有公开截图速度、精度、自动判定成功率等基准。

这些应成为我们需求，不能把截图、批量、知识库或回滚本身宣传为独有优势。我们的差异需要落到更具体、可验收的行为。

### 3.3 从 Pro 修复日志提炼真实风险

- 1.8.1：修复新建预制体自定义脚本丢失、图片粉色缺失贴图；说明“节点生成成功”不足以证明序列化与引用正确。
- 1.8.1：预览未传平台时跟随编辑器下拉选择；默认行为必须符合用户当前编辑器状态。
- 1.8.0/1.7.9：多项目端口、账号冲突、端口切换同步客户端；多开不是只换一个随机端口就验收完毕。
- 1.8.0：代理适配；面向发行的连接诊断需要明确区分本地 MCP、厂商服务和模型服务。

这些是对方声称已修复的历史问题，不能当作当前 Pro 仍然存在的缺陷。

## 4. 我们已有的基础与最大差距

已具备：4 个常驻 MCP 工具、36 项可发现操作；官方 SDK STDIO；带令牌的本机桥接；顺序队列、请求 ID、超时状态；批量参数预检查、结果引用、摘要/字段投影；基础原生编辑、日志/API 发现、窗口截图/输入/菜单；Creator 面板、3 个 UI 模板和有限结构检查。

已有记录为 17 项自动检查、基础 15 项/新版 9 项真实编辑器检查、修复后的 UI 6 项回归。它们是不同检查集，不能合并成“完整编辑器覆盖百分比”。本次为研究和文档更新，没有重跑这些测试。

最大的差距依次是：

1. **完整任务语义：** 预制体、事件/脚本引用、资产关系、动画等还依赖临时发现 API 和编写脚本，成本和失败概率高。
2. **结果验证：** 当前 scene.validate 只做两项检查；截图与结构读取没有组成自动验收流程。
3. **失败恢复：** 顺序 batch 不是事务；UI 失败清理新子树不是任意混合操作的回滚。
4. **运行和交付：** 尚不能自动证明按钮可点击、游戏正确运行、构建产物可启动。
5. **发行体验：** 仍需 Node/仓库安装步骤，其他系统和客户端没有完整验证。

此前 UI 模板不可见就是关键反例：旧实现误用编辑器辅助 Canvas，查询能读到节点，检查器会变化，但正常项目层级和保存都不包含它们。现已使用项目层级白名单、真实 Canvas/Camera、保存重开与截图回归修复。以后所有生成器必须验证结果属于项目并能保存，不能只验证“接口返回成功”。

## 5. “比 Pro 强”的工程规格

### 5.1 三层能力结构

1. **专用操作层：** 把高频 Editor.Message、AssetDB、引擎接口封装成带类型、前置条件和后置断言的稳定操作；覆盖全部公开 Pro 领域。
2. **任务层：** UI 搭建、脚本挂载、预制体生产、运行验证、构建发行等可重放工作流；一次任务可返回多个阶段及真实证据。
3. **扩展与界面层：** 编辑器消息/类型发现、可选输入适配器、第三方插件适配；通用脚本保留为高级出口，明确其撤销和权限边界。

语义 API 优先，必要时操作界面。未知面板先观察、再操作、再确认状态；系统弹窗和第三方扩展单独列兼容范围。没有通用机制能提前保证任意版本、任意插件的所有人工动作永远 100% 成功。

### 5.2 可跟踪需求

### 5.3 成功状态必须分级

| 状态 | 最少证据 |
| --- | --- |
| 已分派 | 请求已送达，有请求 ID；不显示“任务完成” |
| 已修改 | 原生 API 返回，真实项目层级和属性回读符合预期 |
| 已保存 | dirty 检查、磁盘序列化与保存重开结果符合预期 |
| 已显示 | 正确 Canvas/Camera/layer，目标截图能看到内容；截图本身不证明业务交互 |
| 已运行验证 | 预览中的输入及状态断言通过，相关运行错误已检查 |
| 已交付 | 用户要求的场景/预制体/脚本/资源/构建产物齐备，并附验证范围 |

不是所有操作都强制运行预览；按任务选择验证级别，并在结果里列明未执行的检查。更新一个名称不应付出完整视觉回归成本，生成一个可交互菜单则必须测试点击。

## 6. 界面如何做到便捷、直观

**首次使用：** 安装发行包 → 打开面板 → 显示当前工程/Creator 版本 → 选择客户端连接方式 → 检测 → 生成一个可见示例并定位。已存在配置做差异合并和备份，升级不覆盖用户自定义内容。

面板以用户任务组织，而非把全部 JSON 参数铺满：

- **首页：** 当前工程与场景、连接状态、正在执行的任务、常用操作、版本兼容提示。
- **任务：** 自然语言由 AI 客户端解释；面板展示计划、对象、资源变更和预计验证。先修改预览，必要的破坏性动作提供清楚的恢复说明。
- **模板与组件：** 缩略图、用途、适配分辨率、主题；预检查→生成→定位→查看结果。支持用户保存自己的可复用配方。
- **检查与修复：** 按节点和规则定位，显示问题截图/属性差异；选择修复项，修复后重验。
- **历史与恢复：** 成功/部分完成/失败/已恢复，展开步骤、请求 ID、差异和证据；可导出脱敏复现包。
- **高级设置：** 能力目录、准确参数、版本/API 来源、读写和高级入口开关。面向贡献者保留技术细节，默认界面隐藏低频参数。

不要求面板内再建一个模型聊天客户端。先把现有 Codex 对话与 Creator 的状态、计划、结果联动做好，避免重复配置模型和额外 API 费用。

## 7. Token 和效率如何衡量

**已有数据：** 0.5 的旧 30 工具基线 tools/list UTF-8 JSON 为 18,508 字节，4 工具为 3,255 字节，减少 82.4%。实际四项同任务读取从 4 次执行调用降为 1 次，返回 JSON 从 3566 降为 672 字节；首次批量 schema 发现另计 1 次、3039 字节返回。三轮交替测试的耗时等细节在 `artifacts/workflow-benchmark.json`。这是自身模式比较，没有模型真实 Token 或 Pro 同任务实测。

| 手段 | 目的 | 必须防止的反效果 |
| --- | --- | --- |
| 4 个常驻入口 + 目录按需发现 | 少加载无关 schema | 每次调用都重查目录；需按服务版本缓存，兼顾首次发现成本 |
| 专用任务/配方 + batch 结果引用 | 少往返、少传中间 UUID | 批次太大难排错；保留步骤状态及精确失败点 |
| 默认摘要/字段投影/分页 | 少返回无关大对象 | 摘要省掉失败、截断、dirty 或验证信息 |
| 事件游标/版本戳/结构差异 | 少重复读整棵树 | 过期缓存、漏掉用户手动编辑、场景切换混用 |
| 截图裁剪/缩放/按阶段触发 | 少图像输入成本 | 看不到关键区域，过度缩小导致文字与错误不可读 |
| 元数据知识按需检索 | 少猜字段、少试错 | 注入整本引擎文档、无来源的过期建议 |
| 业务后置断言 | 提高一次成功率 | 为省一次调用而留下隐性错误，导致后续大量返工 |

Streamable HTTP 解决连接与传输能力，不自动保证 Token 更便宜；4 个工具也不自动优于 16 个工具。需要优化**完成同一正确任务的总成本**。

评测固定 Creator、项目、资源、模型、客户端、起始上下文及成功条件；区分冷启动/已有目录缓存。记录任务成功率、输入/输出 Token、缓存 Token、图像开销、调用次数、耗时、人工介入、重试和恢复结果。拿不到客户端真实使用量时，只报告字节数/调用数等代理指标。

建议的内部目标（尚未达成）：固定 10 个高频任务，每项运行至少 5 次；至少 95% 满足验收，严重数据丢失为 0；有合法可运行 Pro 对照时，在任务成功率不下降前提下争取总 Token 中位数降低 25%、调用次数中位数降低 30%。若无 Pro 对照，只报告自身版本趋势。样本量较小，应同时展示原始结果和失败案例，不包装为所有项目的成功率。

## 9. 实施顺序与发布门槛

| 阶段 | 主要范围 | 必须交付的真实产物 / 门槛 |

先把 A 做到可用，再扩展 B；不能先堆到 300 个操作却让 UI 不可见、引用丢失。路线按门槛推进，不承诺缺乏依据的工期。

## 10. 独立实现与许可边界

公开版 README.EN 的许可限制源码及衍生代码商业使用，并非 MIT。我们的功能设计可以参考公开说明，但实现须独立编写，调用 Cocos 官方 API 和自有适配；不直接搬运其 TS/Vue/知识库/资源，也不反编译或分发 Pro。第三方参考克隆、用户工程、日志、令牌和授权数据不进入发行包。

本项目当前采用自有的个人非商业许可，商用及再分发须书面授权，详见 [LICENSE](../LICENSE) 与 [许可说明](LICENSING.md)。公开源码和独立实现都不等于允许未经授权的商业使用；双方的授权条件与功能/性能验收分别评价。

VberAI Studio 的设计导入、资产生成、抠图等属于独立平台，不能全部算作 Cocos MCP Pro 已内置功能。我们可提供设计稿/资源导入接口与适配器，生成服务按用户选择接入，不把需要另一个云服务的能力宣传成离线 MCP 自带。

需要后续 Pro 实测才能回答的问题：完整 schema 与 231 项口径、回滚范围、视觉校验机制、运行时/构建终态、Codex 实测、跨系统/多项目表现、真实 Token 基准。当前分析和研发无需等待这些信息；有合法试用环境后按相同任务追加对照报告。
